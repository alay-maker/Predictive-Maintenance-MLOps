El Problema de Negocio

  • Mantenimiento Reactivo: Reparar tras la rotura.
  • Impacto: Paradas de línea imprevistas (Downtime).
  • Dato Crítico: 1 hora de parada cuesta hasta 100x más que el mantenimiento programado.
  • Necesidad: Actuar antes del fallo usando telemetría.

Guion (0:30 - 2:00)

"El cliente es una planta de manufactura (CNC). Actualmente el 80% de su mantenimiento es reactivo: la máquina se rompe, la producción para, y pierden dinero a raudales. El problema es que los sensores generan datos, pero nadie los evalúa en tiempo real. Necesitan un sistema que lance alertas predictivas submilisegundo *antes* de la rotura catastrófica."

¿Por qué MLOps?

  • Sin MLOps: Un notebook local, datos en CSV, modelo manual que se desfasa en 2 días.
  • Con MLOps: Push a GitHub → Tests automáticos → Despliegue en Azure → Monitoreo continuo.
  • Garantías: Reproducibilidad, trazabilidad y baja latencia en streaming.
Guion (2:00 - 3:30)

"Un notebook .ipynb que funciona en local no es un producto. Un pipeline MLOps garantiza que nuestro modelo de árbol de decisión llegue a Azure de forma segura y automatizada."

  • Si el profe pregunta "¿Por qué CI/CD?": "Sin CI/CD, si alguien toca el código del worker, podríamos romper la ingesta en producción sin darnos cuenta."

Arquitectura del Pipeline

1. CI / GitHub Actions

Tests automatizados (pytest).
Validación de cobertura > 70%.

Conexión SSH a Azure.
Docker Compose Build.

3. Inferencia (Azure)

Redis Streams (Mensajería).
Workers Escalables (ML).

Guion (5:00 - 7:30)

"La arquitectura tiene tres capas. El repo de GitHub es el centro de control. El archivo azure-deploy.yml ejecuta los tests y el CD mediante SSH hacia la VM de Azure. Allí, Docker Compose levanta la red interna con Redis (imagen oficial), el Productor y los Workers."

  • Si el profe pregunta por qué Redis: "Porque necesitamos procesar en streaming real, no en batch. Redis Consumer Groups permite balancear la carga entre workers."

El Gate de Calidad MLOps

  • Job CI: pytest --cov=src tests/
  • Umbral: Cobertura > 70%.
  • Fallo (Exit 1): Detiene el Workflow. NO hay pase a producción (CD).
  • Protección: Previene la caída de la ingesta de telemetría.

Caso Real: Sprint 2

Un error de sintaxis en worker.py tiró la cobertura al 40%. El Gate bloqueó el pase a Azure. Sin esto, habríamos roto el broker de mensajería en producción.

Guion (7:30 - 9:00)

"Este es el corazón MLOps. En azure-deploy.yml, configuramos que si el test reporta menos de 70% de cobertura, el CD se cancela. Esto no es teórico: en el Sprint 2 subimos un cambio que rompió el worker. El gate lo cazó y evitó que desplegáramos un contenedor corrupto en Azure que habría detenido el análisis de la maquinaria entera."

Conclusiones y Recomendaciones

  • 1. Reproducibilidad: Un pipeline MLOps garantiza que el modelo local sea el mismo que infiere en Azure.
  • 2. El Gate es Vital: Condicionar el despliegue a los tests (GitHub Actions) evita caídas catastróficas en el entorno productivo.
  • 3. Escalabilidad Redis: Usar Consumer Groups permite escalar de 1 a N workers simplemente alterando el comando de Docker, absorbiendo picos de telemetría.
  • Recomendación a Futuro: Implementar detección de Data Drift (Ej. Evidently AI) y reentrenamiento automático. Las máquinas sufren desgaste, y los umbrales de vibración cambian con los años.
Guion (15:00 - 16:30)

¿Qué haríamos Diferente?

Lo que NO repetiríamos:

  • Subestimar el tiempo de configuración de las Network Security Groups en Azure.
  • Hardcodear IPs temporalmente (solucionado pasando a GitHub Secrets).
  • Copiar el código completo en cada contenedor en lugar de usar multi-stage builds.

Lo que añadiríamos:

  • Branch Protection: Bloquear direct pushes a main desde el inicio.
  • ADRs: (Architecture Decision Records) para documentar por qué elegimos Redis frente a Kafka.
